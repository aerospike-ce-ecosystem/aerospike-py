## 1차 검증 — Rust 2.2에서 결함과 호환 기준 고정

- [x] 통합 브랜치에서 시작한다. 공식 `aerospike==18.1.0`과 두 Python 클라이언트(sync·async)에 동일한 초기 레코드·연산·정책을 적용한다. 18.1.0은 `uv.lock`의 고정값이며, 19.x로 올리는 일은 이 작업과 분리한다. 쓰기가 포함된 비교는 클라이언트마다 레코드를 초기화한다. 아래 표를 실행 가능한 비교 테스트로 남긴다.
- [x] 1차에서는 **공식 클라이언트의 기대값만 고정한다.** Rust 2.2는 bin을 `HashMap`으로 돌려줘 순서와 중복을 복원할 수 없으므로, 바인딩 측 비교는 `xfail(strict=True)`로 둔다. 2차에서 이 xfail과 기존 skip 5개를 함께 해제한다.
- [x] 잘못된 `exists`·`gen`은 전송 전에 거부한다. 같은 파서의 `commit_level`·`replica`·`read_mode_ap`·`expected_duration`도 알 수 없는 값을 기본값으로 바꾸지 않고 거부한다. 기존 값과 generation이 유지되는지 확인한다. `LazyBatchRecords`의 `len(handle)`은 고유 Mapping 키 수, `found_count()`는 성공 행 수, `to_list()`는 요청 순서와 슬롯 수를 보존한다. `to_dict()`는 바깥 dict의 얕은 복사임을 명시한다. [정책 파서](../rust/src/policy/mod.rs) · [배치 결과](../rust/src/batch_types.rs)
- [x] 아래 NumPy 계약을 구현하고 현재 release wheel과 비교한다. 1차 커밋은 통합 브랜치에 별도 커밋으로 남기고, squash 병합 뒤에도 브랜치를 지우지 않는다. Rust 3.0 전환의 영향을 따로 측정하기 위해서다.

### `operate_ordered()`의 판정 기준

한 번의 원자적 서버 `operate` 요청으로 `OperateOrderedResult(key, meta, ordered_bins)`를 반환한다. 비교 대상은 `BinTuple(name, value)`의 **목록 전체**다. 공식 Python 18.1.0과 CE 8.2.0.1의 기본 정책에서 관찰한 결과는 다음과 같다. 2026-11-21에 같은 조합으로 다시 실행해 모든 행을 재현했다.

| 요청과 초기값 | 공식 클라이언트의 ordered bins |
|---|---|
| `read(c), read(a), read(c), read(b)` | `[("c", 3), ("a", 1), ("c", 3), ("b", 2)]` |
| `increment(x, 1), read(x)`, 기존 `x=2` | `[("x", 3)]` |
| `write(x, 7)` | `[]` |
| `touch(), read(b)` / `read(없는 bin), read(b)` | 두 경우 모두 `[("b", 2)]` |
| `list_append(l, 3), read(l)`, 기존 `l=[1]` | `[("l", 2), ("l", [1, 3])]` |
| `list_clear(l), read(l)`, 기존 `l=[1]` | `[("l", [])]` |
| `write(x, 7), list_size(l)`, 기존 `l=[1]` | `[("l", 1)]` |
| `write(x, 7), map_size(m)`, 원소 한 개인 map | `[("x", None), ("m", 1)]` |
| `read(없는 bin), map_size(m)` | `[("없는 bin", None), ("m", 1)]` |
| `increment(x, 1), read(x), map_size(m)`, 기존 `x=2` | `[("x", None), ("x", 3), ("m", 1)]` |
| `touch(), map_size(m)` | `[("m", 1)]` |
| `write(x, 7), bit_count(b)` / `expression_read(r)` / `hll_get_count(h)` | `write`가 `("x", None)`으로 나타난다 |

**판정 규칙.** 공식 클라이언트는 요청에 map·bit·HLL·expression 연산이 하나라도 있으면 서버에 모든 연산의 응답을 요구한다. 이때 bin 이름이 있는 연산은 값이 없어도 `(name, None)`으로 나타나고, `touch()`처럼 이름이 없는 연산은 항목을 만들지 않는다. 그런 연산이 없으면 값을 돌려준 연산만 나타난다. list 연산은 이 모드를 켜지 않는다. 18.1.0의 `operate_ordered()`는 정책 dict로 이 동작을 바꾸지 못했다.

Rust 3.0은 쓰기 연산이 하나라도 있으면 같은 응답 요구(`RESPOND_ALL_OPS`)를 항상 켠다. 그래서 요청과 `Record.results`를 단순히 `zip`하거나 모든 `Nil`을 제거하면 위 계약이 깨진다. **요청의 연산 종류로 모드를 정하고, 서버가 반환한 순서대로 이름과 값을 함께 보존한다.** 전체 bin 읽기처럼 응답 하나가 여러 결과로 확장되는 조합이 Rust 3.0.0 공개 API로 복원되지 않으면 응답 파서의 최소 upstream 변경을 검토하고, 필요하면 검증한 패치 커밋을 고정한다. 기존 `operate()`의 dict·스칼라 반환은 유지한다. sync·async는 변환기를 공유하고 기존 ordered 호환성 skip 5개를 해제한다. [호환성 테스트](../tests/compatibility/test_operate_ordered.py) · [공식 구현](https://github.com/aerospike/aerospike-client-python/blob/18.1.0/src/main/client/operate.c#L1070)

### NumPy 읽기·쓰기 계약

| 영역 | 구현과 검증 기준 |
|---|---|
| 입력 API | `batch_write_numpy(data, namespace, set_name)`에서 `data.dtype`을 사용한다. 기존 네 번째 위치 인자와 `_dtype=` 키워드를 유지한다. 명시한 dtype과 배열이 다르면 **첫 행 전송 전** `ValueError`를 낸다. |
| 레이아웃·소유권 | 양방향이 이름·offset·itemsize·byte order·`subdtype`·shape를 같은 규칙으로 검증한다. object를 포함한 중첩 dtype, 가변 길이 `StringDType`, 비네이티브 endian은 명확히 거부한다. 1차원 연속·슬라이스·역순·빈 배열을 테스트한다. 변경 가능한 Python 버퍼의 raw pointer를 비동기 작업으로 넘기지 않고, 읽기의 GIL 해제 구간을 보존한다. |
| 벡터와 수치 | `(1,)`도 벡터다. 새 쓰기는 shape에 맞는 BLOB으로 저장하고, 읽기는 종전 scalar도 길이 1 벡터로 받아들인다. 벡터 BLOB 길이 불일치는 오류로 처리한다. 고정 문자열 `S<N>`의 기존 패딩·절단 규칙은 유지한다. 유한값의 f16/f32 overflow는 `OverflowError`, 원래 NaN·±inf는 보존한다. |
| 키·행 | 출력 행 `i`는 입력 행 `i`와 대응한다. digest-only 행은 위치로 접근하며 사용자 키 인덱스에 합성 문자열·정수를 넣지 않는다. 실제 키 중복은 마지막 행을 가리킨다. 실패 행도 위치와 `result_codes`를 보존한다. Rust와 Python 경로에 동일 테스트를 적용한다. |

NumPy 2.5.5는 Python 3.12 이상이 필요하다. 패키지의 Python 3.10·3.11 지원을 유지하고, 이 환경은 설치 가능한 NumPy 2.x를 테스트한다. 우선 볼 파일은 [네이티브 변환](../rust/src/numpy_support.rs), [Python 변환](../src/aerospike_py/numpy_batch.py), [NumPy 경계값 테스트](../tests/integration/test_numpy_batch_edge_cases.py), [GIL 회귀 테스트](../tests/concurrency/test_gil_detach_to_numpy.py)다. [NumPy 2.5.5 배포 정보](https://pypi.org/project/numpy/2.5.5/)

## 검증 기록과 단일 릴리스

1. **기준값을 재현한다.** 이전 조사에서 2.2 바인딩은 Rust 318개, Python 단위·통합 1,477개, 공식 호환성 209개가 통과했다. 별도 NumPy 2.5.5 실행에서는 관련 테스트 101개가 통과했다. CPython 3.13.11, CE 8.2.0.1 단일 노드, release wheel, 720행 × float64 8필드, 경쟁 작업 없음, 워밍업 5회 후 51회 중앙값은 기존 핸들 `to_numpy` **0.113 ms**, 전체 읽기 **6.195 ms**, 전체 쓰기 **8.203 ms**였다. 이는 변경 전 참고치다. 이 수치를 내는 스크립트를 [`benchmark/numpy_microbench.py`](../benchmark/numpy_microbench.py)로 저장소에 두고, 경쟁 CPU 작업을 넣은 기준값도 변경 전에 함께 잰다. 경쟁 작업 없는 마이크로벤치는 GIL 점유 회귀를 놓친다.
2. **두 단계에서 동일하게 검증한다.** 서버를 준비한 뒤 `make test-rust`, `AEROSPIKE_REQUIRE_SERVER=1 make test-integration`, `AEROSPIKE_REQUIRE_SERVER=1 make test-compat`, `make test-unit`, `make test-concurrency`를 실행한다. 최종 단계에서 lint·typecheck·문서 빌드, 최소 Rust 버전, 지원 플랫폼 wheel 설치, CPython 3.13·free-threaded, 고정 서버 7.2·8.1·8.2 및 다중 노드 장애를 확인한다. CI 통합 매트릭스도 `latest` 대신 이 세 버전으로 고정한다. 로컬 `make run-aerospike-ce`는 CE 8.1.0.3을 띄우므로, 8.2 기준값과 비교할 때는 같은 이미지로 맞춘다. 기존 패키지가 쓴 레코드를 **최종 wheel**로 읽는다. 경쟁 Python 작업을 넣어 p50/p95/p99·처리량·이벤트 루프 지연·최대 RSS를 전후 비교하고 커밋, 환경, skip 사유를 기록한다. [Makefile](../Makefile) · [벤치마크](../benchmark/gil_starvation.py) · [과거 성능 회귀](../POSTMORTEM-v0.5.6-batch-regression.md)
3. **한 번 병합하고 배포한다.** 1차·2차 커밋을 같은 통합 브랜치의 `main` 대상 draft PR에서 검증한다. hot path를 건드리므로 PR을 열기 전에 `perf-impact-reviewer` 판정이나 벤치마크 결과가 있어야 한다. 없으면 `gh pr create`가 훅에서 거부된다. 중간 커밋은 통합 브랜치에 둔다. `main`에 배포 대상 변경이 들어가면 매일 한국 시간 07:00 자동 릴리스 대상이 된다. 최종 squash 제목은 `feat!:`를 사용하고, 릴리스 시점에도 최신 minor가 `0.14`이면 목표는 **`v0.15.0`**이다. 한 번의 GitHub Release 발행이 wheel·sdist의 PyPI 게시를 시작한다. [CI 트리거](../.github/workflows/ci.yaml) · [버전 계산](../.github/workflows/daily-release.yml) · [게시 조건](../.github/workflows/publish.yaml) · [PR 게이트](../.claude/hooks/pr-perf-gate.sh)
4. **사용자 마이그레이션을 한 곳에 설명한다.** 위치는 문서 사이트의 [`guides/migration-0.15.md`](docs/guides/migration-0.15.md)와 한국어 번역이다. ordered 중복 항목과 조건부 `None`, Mapping 길이, NumPy 합성 키 제거·dtype 검증·벡터 길이·overflow, 쓰기 재시도와 부분 실패에 대해 변경 전후 예제를 싣는다. 특히 `(1,)`은 **서버 저장 타입이 scalar에서 BLOB으로 바뀐다.** 같은 bin을 공유하는 모든 reader가 두 형식을 읽을 수 있게 배포한 뒤 writer를 전환한다. **writer를 전환한 뒤에는 0.14.x로 되돌릴 수 없다.** 0.14.x reader는 `(1,)` 필드의 BLOB을 `TypeError`로 거부한다.

**`make build` 뒤에는 테스트 의존성을 다시 설치해야 한다.** `make build`는 `uv sync --group dev`를 거치고, 이 sync는 dev 그룹 밖의 패키지(공식 클라이언트 `aerospike`, FastAPI, gunicorn 등)를 지운다. 그 상태로 전체 스위트를 돌리면 `tests/compatibility`의 수집 단계에서 `could not import 'aerospike'`로 몇 초 만에 끝난다. 최종 검증에서 한 번 겪었다. `uv sync --inexact --no-install-project --group dev --group test-all --group test-compat`로 되돌린다.

**재시작 테스트 뒤에는 서버를 비워야 한다.** 앞선 검증(`358edc6`)에서 개발 빌드 스위트는 첫 실행에 16개가 실패했고, namespace를 비운 뒤 모두 통과했다. 코드 문제가 아니다. `-m destructive` 테스트가 서버를 재시작하는데, 개발 서버의 namespace는 파일에 저장되고(`storage-engine device`) 테스트는 일반 삭제로 정리한다. 일반 삭제는 디스크에 흔적을 남기지 않으므로 재시작하면 지웠던 레코드가 되살아난다. 실제로 테스트가 지운 키 `bw_exists_create_new`가 재시작 뒤 `gen=1`로 다시 있었다. 그래서 "새 키"를 가정한 테스트가 다음 실행에서 한 번 실패하고(`CREATE_ONLY`가 `KEY_EXISTS`, generation이 2 대신 4), 그 실행의 정리가 끝나면 다시 통과한다. 재시작 테스트를 돌린 뒤에는 `podman exec aerospike asinfo -v "truncate-namespace:namespace=test"`로 비운다.

free-threaded 실행은 `tox -e py314t,freethreading-py314t`가 아니라 3.14t 인터프리터로 wheel을 직접 빌드해 같은 두 스위트를 돌린 것이다. 이 기계의 tox(4.34.1, tox-uv 1.29.0)는 패키징 환경 `.pkg-cpython314`를 Homebrew의 GIL 빌드 3.14로 만들어 `cp314` wheel을 내놓고, 3.14t는 그 wheel의 네이티브 모듈을 import하지 못한다. 작업 초기에는 같은 명령이 통과했다. 브랜치는 tox 설정을 건드리지 않았으므로 `main`에서도 같을 것이다.

**0.14.4와의 데이터 호환.** 0.14.4가 쓴 레코드와 브랜치가 쓴 레코드를 두 빌드가 서로 읽어 같은 값을 얻었다. 대상은 스칼라, 정수·bytes 키, TTL, CDT, `batch_write`, `(4,)` float32 벡터를 포함한 NumPy 행, `to_numpy`의 bytes, scan이다. 예외는 마이그레이션 가이드에 적은 `(1,)` 벡터 하나다. 언어별 blob(particle type 7~12) 여섯 종은 브랜치에서 모두 `bytes`로 읽히고, 0.14.4에서는 `RustPanicError`가 난다.

### 성능 (0.14.4 → 브랜치)

같은 기계, 같은 서버, NumPy 2.5.5, release wheel로 쟀다. 빌드는 셋이다.

- **0.14.4**: PyPI 패키지.
- **리뷰 전**: PR 전 리뷰의 수정이 들어가기 전 브랜치(`8de0586`의 wheel).
- **최종**: 코드가 마지막으로 바뀐 커밋(`e76a1d1`)의 wheel. 그 뒤의 커밋은 문서와 stub만 바꾼다.

수치는 빌드를 번갈아 3회 돌린 중앙값이다. 클라이언트와 서버(VM)가 한 기계의 CPU를 나눠 쓰므로 3% 안쪽의 차이는 구분되지 않는다. 0.14.4나 리뷰 전 빌드보다 나빠진 것은 [성능에서 치른 비용](#성능에서-치른-비용)에 따로 모았다.

**어느 wheel에서 쟀는가.** query를 읽는 측정 전부, 단건 연산, `batch_write`, HTTP의 s4 gather, 단계별 시간은 `e76a1d1`의 wheel에서 쟀다. `numpy_microbench`, `gil_starvation`, `batch_read`, 경쟁 스레드가 있는 `op_latency`, 나머지 HTTP 시나리오, 메모리, 노드 장애는 재검증의 수정이 들어가기 전 wheel(`358edc6`)에서 쟀고 다시 재지 않았다. 그 사이의 커밋(`a34eed4`~`e76a1d1`)은 기본 정책의 성공 경로에 비용을 더하지 않는다. 성능 검토가 코드를 읽어 확인했고, 모든 await 연산의 결과 변환에 패닉 가드를 씌운 `dcc58e4`는 단건 연산을 다시 재서 확인했다.

### 성능에서 치른 비용

0.14.4나 리뷰 전 빌드보다 나빠진 측정을 모두 적는다. 성능 검토(`perf-impact-reviewer`)의 판정은 브랜치 head까지 `must-bench`이고(차단 없음), 아래 측정이 그 근거다. 검토는 항목을 둘로 나눴다.

**유지보수자의 명시적 승인이 필요한 것.** 요청 경로에서 0.14.4보다 5% 넘게 나빠졌거나, 레코드마다 할당이 있는 경우다.

1. **aerospike-core가 레코드마다 하는 16~24바이트 할당.** 레코드를 정확히 한 번 전달하려고 upstream의 record stream 대신 callback API와 자체 큐를 쓰는데, upstream은 callback이 돌려주는 future를 레코드마다 박싱한다. 바인딩에서 없앨 수 없다. 그 결과 sync `foreach()`는 리뷰 전보다 1~4% 느리다(같은 scan을 잰 세 측정에서 151.6 대 149.6 ms, 149.9 대 147.1 ms, 151.7 대 145.5 ms). 0.14.4(184.9~193.2 ms)보다는 빠르다.
2. **원소 5,000개 list를 읽는 `operate()`**: async 64개 동시에서 처리량 −6.8%, 호출당 CPU +12.6%(180 µs → 203 µs). sync는 처리량 −2.4%, 호출당 CPU +15.1%(138 µs → 159 µs)이고, 앞선 측정에서는 +8.5%, +4.5%였다. sync의 CPU는 측정마다 크게 달랐다. [후속 작업](#후속-작업)에 적었다.
3. **모두 없는 키의 `batch_read`**: 호출당 CPU +5.5~9.0%(5,000키에서 3,790 µs → 4,132 µs, 키당 약 0.07 µs). wall time은 같다. 원인은 조사하지 않았다.
4. **메모리**: 동시 32 배치에서 RSS 184 → 257 MiB(+40%), 50,000키 배치 한 번에 키당 +23%, `gil_starvation`의 최대 RSS +10%. [다음 절](#메모리는-늘었다)에 적었다.
5. **서버가 포화됐을 때 작은 query의 꼬리 지연.** 가장 큰 사례는 256개를 읽는 `results()` 64개 동시다. p99가 186.0 ms 대 79.6 ms, 최장이 292.7 ms 대 91.4 ms이고, 리뷰 전(129.4 ms, 197.1 ms)보다도 길다. 같은 측정에서 초당 호출은 1,193 대 1,078, p50은 46.5 대 59.0 ms, 호출당 CPU는 0.88 대 2.38 ms로 낫다. 동시 64개를 처리량으로 나눈 평균 대기는 54 ms 대 59 ms이므로, 평균은 짧아지고 분포가 넓어진 것이다. 5개를 읽는 query 16개 동시에서도 p99가 54.8 ms 대 39.0 ms다. p50은 7.8 ms 대 10.7 ms로 짧고, 리뷰 전 빌드도 같았다(54.6 ms). 포화 아래(초당 300·600개 도착)에서는 p99도 최종이 짧다. 원인을 좁히려고 세 가지를 더 쟀다. (1) runtime worker를 2·4·8개로 바꿔도 64개 동시의 p99는 181~185 ms로 같다. (2) 동시 개수를 16·32·64로 바꿔도 초당 호출은 세 빌드 모두 1,050~1,200에서 변하지 않는다. (3) 프로세스 둘이 32개씩 동시에 돌리면(서버가 보는 것은 64개) 합계 처리량은 세 빌드 모두 초당 1,130~1,160으로 한 프로세스 때(1,078~1,193)와 같은 수준이고, 각 프로세스의 p99는 최종 179~193 ms, 리뷰 전 185~193 ms, 0.14.4 103~108 ms다. 32개만 돌릴 때의 p99는 95.8, 69.6, 52.8 ms다. 즉 처리량의 한계는 서버에 있고, 꼬리는 클라이언트가 동시에 건 개수가 아니라 서버에 걸린 개수를 따른다. 리뷰 전 빌드가 한 프로세스에서 짧았던 것은 리뷰 수정 때문이 아니다. 둘로 나누면 최종과 같아진다. 작은 결과를 이벤트 루프에서 변환하게 한 `a34eed4`도 원인이 아니다. 루프 하나의 부하를 반으로 줄여도 꼬리는 그대로이고 루프 지연 p99는 3.8 ms다. 0.14.4가 같은 구성에서도 짧은 이유는 확인하지 못했다. 0.14.4는 호출당 CPU를 2.7 ms 쓰고(최종 0.97 ms) 호출의 중앙값은 더 길다(53~56 대 48~50 ms).

**인지만 하면 되는 것.** 리뷰 전 빌드보다 나빠졌지만 0.14.4보다는 낫거나 같다.

- **2노드에서의 CPU.** 리뷰 전보다 sync `foreach()`가 wall +4.4%, CPU +11%(0.200초 → 0.223초), `async for`가 CPU +4%, sync `results()`가 CPU +2%다. 자체 큐에 reader 둘이 넣는다.
- **`record_queue_size`를 작게 주면 리뷰 전보다 느리다.** 64에서 169.8 ms(CPU 0.27초), 16에서 176.2 ms(0.31초)다. 리뷰 전 빌드는 upstream의 record stream을 썼고 큐 크기와 무관하게 146~148 ms(0.20초)였다. 자체 큐는 가득 차면 reader가 기다리는 경로를 타고, 그 경로에는 할당과 깨우기가 있다. 그 비용을 따로 재지는 않았다. 기본값 1024에서는 1~4% 차이다.
- **큰 결과 옆의 중간 결과.** 10만 레코드 `results()` 3개가 도는 동안 500 레코드 `results()`의 p50이 12.9 ms로 리뷰 전 7.5 ms보다 길고, 8초 동안 끝낸 호출도 415개 대 751개다. 이벤트 루프 지연 p99는 58.0 ms 대 38.5 ms다. GC를 끄면 p50 11.5 대 6.5 ms, 호출 621개 대 1,105개이고 루프 지연 p99는 19.3 대 18.2 ms로 같다. 256개를 넘는 결과는 변환 차례를 기다리기 때문이다([결정 기록](#결정-기록) 참고). 차례를 두지 않으면 중간 결과가 몰릴 때 루프가 밀린다(위 표의 1,000 레코드 24개 동시). 0.14.4는 같은 상황에서 p50이 374.0 ms(GC를 끄면 137.8 ms)였다.
- **async `foreach()`의 wall time은 측정이 엇갈렸다.** `358edc6`의 wheel에서는 0.14.4보다 5~11% 길었다(10만 레코드 200.0 대 191.3 ms, 20만 레코드 438 대 394 ms). 최종 wheel에서는 같거나 짧다(10만 레코드 194.8 대 196.0 ms, 20만 레코드 379 대 396 ms, 다시 재서 392 대 391 ms). 두 wheel 사이에 `foreach()` 경로를 바꾼 커밋은 없으므로 측정 시점의 차이로 본다. CPU는 두 번 모두 0.38~0.39초에서 0.22~0.23초로 줄었다. 0.14.4는 sync `foreach()` 전체를 worker 스레드 하나에서 돌렸고, 지금은 256개 배치마다 이벤트 루프와 worker 스레드를 오간다. 그 대신 취소와 중단이 배치 단위로 듣는다. 처음에는 승인이 필요한 항목이었고, 최종 측정에서 재현되지 않아 성능 검토가 이쪽으로 옮겼다.
- **2만 레코드 결과 8개 동시의 루프 지연 p99는 측정마다 순서가 바뀐다.** 최종 측정에서는 30.8 ms 대 리뷰 전 22.4 ms, 앞선 측정에서는 19.9 ms 대 23.4 ms였다. 최장 지연은 두 번 모두 비슷하다(36.8 대 39.8 ms, 45.3 대 40.4 ms). 0.14.4는 252 ms다.
- **GIL을 놓지 않는 스레드 옆의 async `results()`는 0.14.4와 같은 수준에 머문다**(0.59초 대 0.56초). 변환 덩어리를 4,096개로 하면 0.40초였지만, 여러 결과가 동시에 돌 때 이벤트 루프 지연 p99가 9 ms에서 24 ms가 되어 1,024개를 골랐다.
- **free-threaded 빌드에서 작은 결과의 변환 위치.** 256개 이하의 결과는 이제 호출자 스레드(이벤트 루프)에서 변환한다. GIL이 있는 빌드에서는 어차피 같은 GIL을 쓰므로 차이가 없다. 3.14t에서는 호출당 최대 약 0.6 ms가 병렬 스레드에서 루프로 옮겨 온다(성능 검토의 추정, 실측 없음).

`.claude/perf-baseline.json`은 저장소에 없어서 비교한 기준선은 위의 0.14.4와 리뷰 전 빌드뿐이다.

### 메모리는 늘었다

처리량과 지연은 같거나 나아졌지만 메모리는 비용이 있다. 재검증의 수정이 들어가기 전 wheel(`358edc6`)에서 잰 프로세스 RSS다. 그 뒤의 커밋은 배치 경로의 메모리를 바꾸지 않는다.

| 부하 | 0.14.4 | 최종 |
|---|---|---|
| 720개 레코드 × 8 bin `batch_read`, 동시 8, 경쟁 CPU 작업 (`gil_starvation.py`, 3회) | 최대 66–70 MiB | 최대 75–77 MiB |
| 같은 배치, 동시 32, 192,000회(약 3분) | 138 MiB에서 184 MiB까지 오르고 멈춤 | 201 MiB에서 257 MiB까지 오르고 멈춤 |
| 50,000키 `batch_read` 한 번, 모두 있는 키 | 키당 2.2 KiB | 키당 2.7 KiB |
| 50,000키 `batch_read` 한 번, 모두 없는 키 | 키당 2.0 KiB | 키당 2.4 KiB |

지속 부하에서 두 빌드 모두 RSS가 계단식으로 오르다가 오르는 간격이 길어진다. 0.14.4는 마지막 42개 구간(53,760회), 최종 빌드는 마지막 28개 구간(35,840회) 동안 변하지 않았다. 누수로 보이지는 않지만 3분보다 긴 부하로 확인한 것은 아니다. 늘어난 원인은 Rust 3.0에 있다. 배치 행 구조체가 약 20% 커졌고(`BatchRecord` 320 → 408 바이트 등), 연결마다 읽기 버퍼가 4 KiB에서 64 KiB가 됐으며, 큰 버퍼를 해제하지 않고 풀에 보관한다(`use_buffer_pool` 기본 켜짐, 크기 등급마다 최대 4 MiB, 약 1분 뒤 해제). 이 설정은 지금 Python에서 바꿀 수 없다. 마이그레이션 가이드에 수치와 함께 적었다.

### 결정 기록

- **Client 기본값.** `timeout`·`idle_timeout`은 30초를 명시적으로 유지한다(3.0은 1초와 0으로 낮췄다). `login_timeout` 5초를 포함한 나머지 기본값은 upstream 값을 받아들였다.
- **재시도 소진.** `result_code`는 `-1`, `error_type`은 `"MaxRetriesExceeded"`다. Java 번호 체계의 클라이언트 코드는 Python으로 내보내지 않는다.
- **`in_doubt`.** 예외, 배치 행, span 속성이 한 함수(`errors::may_have_been_applied`)를 읽는다. upstream 판정을 여섯 곳에서 보정한다. 서버가 `TIMEOUT`으로 답한 쓰기 행은 in doubt로 올린다. UDF 실패는 서버의 확정 응답이므로 내린다. 서버가 거절한 쓰기(`KEY_BUSY`·`DEVICE_OVERLOAD`·`PARTITION_UNAVAILABLE`)는 재시도 횟수가 다해 "시도 소진" 오류로 감싸여 와도 서버 응답을 따라 내린다. 반대로 호출자가 쓰기에 `max_retries > 0`을 준 경우에는 `KEY_NOT_FOUND`·`FILTERED_OUT`·`UDF_BAD_RESPONSE`로 끝난 쓰기 행과 `remove()`의 `RecordNotFound`를 in doubt로 올린다. 첫 전송이 적용된 뒤 재전송이 받은 응답일 수 있는데, Rust client가 그 행을 두 번 보냈는지 알려 주지 않기 때문이다. 같은 조건에서, 재전송할 때 노드를 찾지 못해 클라이언트가 스스로 `PARTITION_UNAVAILABLE`을 찍은 쓰기 행도 올린다. upstream은 "보낸 것이 없으니 확정"이라고 하지만 그 전의 전송은 적용됐을 수 있다. 클라이언트가 만든 코드는 노드 이름이 없다는 점으로 서버의 응답과 구분한다. 기본 정책(쓰기 재전송 없음)에서는 달라지는 것이 없다. 마지막으로, 노드별 작업을 join하지 못해 배치가 행을 하나도 돌려주지 않고 끝나면 쓰기 배치의 응답 없는 행을 in doubt로 올린다. 보내지 않았다고 확신할 수 있는 것은 첫 전송의 라우팅 실패(잘못된 인자·namespace, 노드 없는 파티션)뿐이다.
- **실패한 배치의 예외는 행 하나라도 in doubt면 in doubt다.** 여러 노드에서 실패한 호출은 먼저 실패한 노드의 오류 하나로 올라온다. 그 오류가 확정 거절(`KEY_BUSY`)이어도 다른 노드의 몫은 보내고 답을 못 받았을 수 있다. 예외의 종류는 레코드 순서에 따라 달라질 수 있지만 `in_doubt`는 달라지지 않는다.
- **오류 분류는 마지막 시도를 따른다.** 재시도가 소진되면 upstream은 timeout으로 감싸고 그 아래에 시도들의 오류를 단다. context 메시지가 아닌 첫 원인이 마지막 시도이고, 그것이 분류를 정한다. 마지막 시도가 timeout이면 감싼 timeout이 그대로 남는다. 다중 키 배치는 모든 시도를 최신순으로 이어 붙이므로, 이 규칙이 없으면 가장 오래된 시도의 오류로 분류된다.
- **query의 레코드는 정확히 한 번, 자체 큐로.** upstream의 record stream(`Client::query`)은 라운드를 다시 가져올 때 이미 버퍼에 있던 레코드를 또 전달하므로 쓰지 않는다. callback API(`Client::query_foreach`)는 callback이 레코드를 받은 순간 재개 지점을 옮기므로, 바인딩이 callback에서 자체 큐에 넣고 소비자는 그 큐에서 꺼낸다. 레코드마다 지나는 경로라서 비용을 줄였다. 큐에 자리가 있으면 callback은 복제·할당·대기 없이 넣고, 소비자는 한 번에 최대 64개(허용량의 4분의 1 이하)를 꺼낸다. 큐에 있는 것과 꺼내 놓고 아직 넘기지 않은 것을 합쳐 `record_queue_size`를 넘지 않는다(기본 1024면 큐 961, 꺼낸 것 최대 63).
- **async `results()`는 한 번에 모은다.** 스트림을 배치 단위로 읽으면 배치마다 이벤트 루프를 한 번 거치고, 다른 스레드가 GIL을 쥐고 있으면 그때마다 기다린다. 결과를 어차피 통째로 갖는 `results()`는 런타임에서 GIL 없이 레코드를 모으고, 1,024개씩 별도 스레드에서 변환하면서 `Record`로 감싼다. 이벤트 루프는 끝에 한 번만 관여한다. `async for`와 `foreach()`는 도착하는 대로 넘기는 것이 목적이므로 그대로다.
  - **변환은 프로세스 전체에서 한 번에 한 덩어리만 한다.** 변환은 GIL이 필요해 어차피 겹칠 수 없다. 차례를 두지 않으면 큰 `results()`마다 스레드 하나가 GIL을 요청해, 이벤트 루프 스레드가 그 전부를 제치고 GIL을 얻어야 한다. free-threaded 빌드에서는 나란히 변환한다.
  - **덩어리 크기 1,024는 측정으로 골랐다.** 덩어리가 변환되는 동안 이벤트 루프는 기다리므로 짧을수록 좋다. 반대로 덩어리마다 GIL을 얻어야 하므로, GIL을 놓지 않는 스레드 옆에서는 덩어리 하나에 switch interval(5 ms)을 한 번씩 기다린다. 1,024는 그 상황에서 0.14.x보다 느려지지 않는 가장 작은 크기다.
  - **256개 이하의 결과만 차례 없이, 꺼낼 때 변환한다.** 그보다 큰 결과는 한 덩어리가 안 되더라도 차례를 기다린다. 두 방식을 모두 쟀다. 차례 없이 변환하면 큰 결과 옆의 중간 결과는 빨라지지만(10만 레코드 결과 3개 옆에서 500개 결과가 11 ms 대신 3.5 ms), 중간 결과 여럿이 한꺼번에 오면 다시 GIL 앞에 줄을 선다. 1,000개 결과 24개 동시에서 이벤트 루프 지연이 중앙값 12 ms, p99 54 ms였고, 차례를 두면 0.9 ms, 5 ms였다. 루프를 지키는 쪽을 택했다.
  - **차례는 변환을 기다리던 태스크가 깨어난 뒤에 돌려준다.** 변환 스레드가 GIL을 놓는 순간 바로 넘기면 다음 변환이 GIL을 먼저 잡는 일이 잦아, 같은 시험에서 루프 지연 중앙값이 0.9 ms에서 2.6 ms가 됐다.
  - **결과 리스트는 호출자만 갖는다.** `read_all`은 리스트가 아니라 작은 holder로 끝나고, wrapper가 거기서 리스트를 꺼낸다. asyncio는 await한 future의 결과를 그 태스크가 다음에 이벤트 루프를 거칠 때까지 붙잡으므로, 리스트를 결과로 주면 호출자가 버린 뒤에도 query 전체가 메모리에 남는다. 256개 이하의 결과는 꺼낼 때 호출자 스레드에서 변환한다.
  - **취소된 호출은 줄에서 빠진다.** 기다리던 덩어리는 차례를 받지 않고, 이미 변환 중인 덩어리는 끝까지 변환한 뒤 차례를 돌려준다. timeout으로 취소가 몰릴 때 아무도 기다리지 않는 변환이 살아 있는 호출 앞에 쌓이지 않게 하려는 것이다.
- **sync `results()`는 런타임의 태스크가 모은다.** 호출 스레드가 직접 모으면 큐가 빌 때마다 스레드가 잠들고 reader가 시스템 호출로 깨워야 한다. 태스크로 모으고 호출 스레드는 한 번만 기다린다.
- **빈 레코드는 보내기 전에 거부한다.** `batch_write`의 `(key, {})`는 `InvalidArgError`, bin 필드가 없는 `batch_write_numpy` dtype은 `ValueError`다. upstream은 그런 레코드가 든 노드 몫의 요청을 만들지 않아, 같은 노드의 정상 레코드까지 함께 실패했다.
- **동시 실행 제한.** `apply()`는 `max_concurrent_operations` 슬롯을 차지한다. query·scan 스트림은 일부러 차지하지 않는다. 레코드마다 조회를 하는 소비자가 자기 스트림이 쥔 슬롯을 기다리며 멈추기 때문이다.
- **쓰기 배치 재시도.** 쓰기·삭제·UDF 배치의 `max_retries` 기본값은 0이다. `retry=N`과 0이 아닌 `max_retries`를 함께 주면 `InvalidArgError`다.
- **CI.** 통합 매트릭스를 7.2·8.1·8.2로 고정했고, CodeQL에 Rust(build mode `none`)를 추가했다.

### 작업 중 발견한 것

- **계획에 없던 호환성 변경 세 가지.** 모두 테스트로 고정하고 가이드에 적었다. 알 수 없는 namespace는 `InvalidArgError`가 된다(단건은 `AerospikeTimeoutError`, 배치는 `ClusterError`였다). `meta.ttl`은 초 단위로 계산돼, 쓴 직후 읽으면 설정한 값이 그대로 나온다(0.14.4는 400번 중 398번이 1초 작은 값). `BatchRecord`는 다섯 번째 필드 `error_type`이 생겨 네 이름으로 풀어 쓰는 코드가 깨진다.
- **`where()` 두 번.** 커밋 메시지는 동작 변경처럼 적었지만 0.14.x도 `InvalidArgError`를 냈다. 바뀐 것은 메시지뿐이다.
- **노드 재시작.** 같은 주소에서 노드 ID가 바뀌어 재시작하면 약 1초(tend 주기 한 번) 동안 그 노드로 라우팅하지 못한다. 2.2에서는 수 ms였다.
- **Rust client 3.0의 동작 열 가지를 바인딩에서 보정하거나 피해 갔다.** upstream에 보고할 만하지만 **보고하지 않았다.** (1) 배치가 일찍 반환하면 자리표시 행이 남는다. (2) 서버가 `TIMEOUT`으로 답한 배치 쓰기 행을 in doubt로 표시하지 않는다. (3) 실패한 UDF 호출을 전부 in doubt로 표시한다. (4) record stream을 drop해도 노드별 reader가 멈추지 않는다. (5) 취소(`QueryHandle::cancel()`, 이전에는 `Recordset::close()`)가 소켓 읽기에 막혀 있는 reader를 깨우지 못한다. 속도 제한(`records_per_second`) scan은 서버가 다음 블록을 보낼 때까지 서버에 남는다. 초당 50 레코드에서 45초였고 `socket_timeout`(2초·30초·0)과 무관했다. 이것은 보정하지 못하고 문서에만 적었다. (6) record stream API(`Client::query`)는 라운드를 다시 가져올 때 이미 버퍼에 있던 레코드를 한 번 더 전달한다(at-least-once). 바인딩은 callback API(`Client::query_foreach`)와 자체 큐로 바꿔 정확히 한 번을 지킨다. (7) 서버가 거절한 쓰기를 "시도 소진" 오류로 감싸면서 in doubt로 표시한다. (8) 배치 행이 일반 레코드 경로로 읽는 응답(`KEY_NOT_FOUND`·`FILTERED_OUT`·`UDF_BAD_RESPONSE`)에는 "두 번 보냈으면 in doubt" 규칙이 적용되지 않는다. (9) 배치를 재전송할 때 노드를 찾지 못한 행에 `PARTITION_UNAVAILABLE`을 찍으면서 "보낸 것이 없다"는 이유로 in doubt로 표시하지 않는다. 그 행은 한 번 전에 보낸 행이다. (10) 단건 명령의 재시도 루프가 재전송 시점의 라우팅 오류(잘못된 인자·namespace 종류)를 표시 없이 그대로 돌려준다. 이것은 보정하지 못했다(아래 참고).
- **범위 밖에서 본 것.** `batch_operate`는 레코드별 `exists`·`gen`·`commit_level`을, `batch_remove`는 `exists`를 무시한다. NumPy의 Rust 경로와 Python 경로는 일부 잘못된 값에 서로 다른 예외를 내고, Python 경로는 byte order가 뒤집힌 필드를 받아들인다. 고치지 않았다.
- **테스트 세 건을 타이밍과 무관하게 고쳤다.** 쿼리 중간 timeout 테스트, 2노드 재시도 시나리오의 단정 두 개, `meta.ttl <= ttl` 단정 18개다. 모두 클라이언트 동작이 아니라 한가한 기계의 타이밍을 가정하고 있었다.

재검증에서 나온 수정은 리뷰어의 재현 스크립트로 다시 확인했다. 재전송하지 못한 행은 같은 재현에서 모순이 0개가 됐고(수정 전 3회에 610개), 여러 노드에서 실패한 배치의 예외는 레코드 순서와 무관하게 `in_doubt=True`가 됐으며, 거절된 키 하나짜리 배치의 경고는 8건에서 0건이 됐다. 최종 wheel에서 256개 결과의 변환 패닉은 `RustPanicError`로 올라오고(수정 전에는 8초 동안 응답 없음), 2.6초짜리 scan에 1초 뒤 SIGINT를 보내면 `foreach()`는 0.2초 뒤에, `results()`는 반환할 때 `KeyboardInterrupt`를 올린다.

재검증이 확인하지 못한 것: 노드가 실제로 빠지는 경우의 `08ea4ed`(클라이언트를 닫는 방법으로만 재현했다), OpenTelemetry span 속성, Python 3.10~3.12.

**고치지 않고 문서에만 적은 것.** `max_retries > 0`인 단건 쓰기가 재전송을 기다리는 동안 클라이언트를 닫으면 `InvalidArgError`("Partition map empty")가 `in_doubt=False`로 올라온다. 첫 전송은 적용됐을 수 있다. upstream이 이 라우팅 오류를 표시 없이 돌려주고, 바인딩은 이것을 아무것도 보내지 않은 "모르는 namespace"와 구분할 수 없다. 노드가 죽는 경우는 이 경로가 아니다. 그때는 시도가 소진되어 in doubt로 표시된다. 배치 재검증이 찾았고 수정 전 빌드도 같았다. `operate_ordered()`는 세 경우에 공식 클라이언트와 다르다. bin 이름이 없는 연산(`touch`·`delete`)은 결과에 나오지 않는데, 공식 클라이언트는 map·bit·HLL 연산이 섞인 요청에서 `delete`를 `("", None)`으로 낸다. 쓰기가 있고 map·bit·HLL 연산이 없는 요청에서 nil을 읽은 list 연산은 빠지는데, 공식 클라이언트는 `("l", None)`을 낸다. `MAP_RETURN_KEY_VALUE`는 `(key, value)` 튜플의 리스트이고 공식 클라이언트는 평평한 리스트다. 그리고 클라이언트를 닫아도 이미 읽고 있던 스트림은 쥐고 있는 연결로 끝까지 읽는다.

**재현하지 못한 의심 네 건.** 배치·오류 리뷰어가 재현 없이 코드만으로 제기했다. 세 건은 코드상 실제로 가능한 경로여서 `195ff82`·`2cd260e`·`8337150`으로 고쳤다. 패닉 경로는 건강한 클러스터로 만들 수 없어 단위 테스트로만 고정했다. 남은 한 건은 `batch_write(retry=N)`이 여러 시도에서 호출 전체가 실패했을 때 마지막 시도의 예외를 올린다는 점인데, 행마다의 상태는 `partial_result`에 그대로 있으므로 바꾸지 않았다.

### 로컬에서 확인하지 못한 것

- Linux aarch64, Windows, macOS x86_64의 wheel은 릴리스 빌드에서만 확인할 수 있다. PR의 CI는 Linux x86_64에서 빌드하고 테스트한다.
- `tox -e py314t`는 이 기계에서 wheel을 GIL 빌드 3.14로 만들어 실패한다([테스트](#테스트) 참고). CI의 free-threaded job(3.14t, 3.15t)은 PR에서 통과했으므로 이 기계의 tox 환경 문제다.
- 재전송 시점에 노드를 찾지 못한 쓰기 행의 `in_doubt`(`08ea4ed`)는 두 전송 사이에 클라이언트를 닫는 방법으로만 재현했다. 노드가 클러스터에서 빠지는 경우는 코드로는 같은 경로이지만 돌려 보지 못했다.
- 노드별 작업이 패닉하는 경로(`195ff82`)와 timeout 아래 여러 시도가 이어진 오류(`2cd260e`)는 건강한 클러스터로 만들 수 없어 단위 테스트로만 고정했다.
- **넓은 레코드의 동시 `results()`는 재지 못했다.** 세 번째 성능 검토가 요청한 측정이다(레코드당 2~4 KB, bin 20개 이상, 8개 동시). 이 부하를 걸면 podman VM의 가상 네트워크가 멈춘다. 게스트 커널이 `virtio_net eth0: NETDEV WATCHDOG: transmit queue 0 timed out`을 반복하고, 포워딩된 포트와 ssh가 모두 `connection reset`이 된다. 두 번 시도해 두 번 다 그랬고(한 번은 0.14.4 빌드로 읽는 중이었다), 그때마다 VM을 재시작해야 했다. 클라이언트가 아니라 VM 스택(krunkit 1.1.1, gvproxy)의 문제다. 덩어리 크기는 레코드 수로 정하므로 레코드가 아주 넓으면 한 덩어리의 변환이 길어진다. 레코드 사이에서는 `Record`를 만드는 Python 코드가 실행되므로 기다리는 스레드가 switch interval(5 ms)마다 GIL을 가져갈 수 있다는 것이 근거이고, 실측은 없다. Linux에서도 재지 않았다.
- **VM 재시작에는 설치본의 podman이 필요했다.** 이 기계의 PATH에는 Homebrew의 podman 6.1.0이 있고 VM을 띄우는 `krunkit`은 설치본(`/opt/podman`, 5.7.1과 함께 온 1.1.1)이다. 6.1.0의 `podman machine start`는 `krunkit exited unexpectedly with exit code 2`로 실패하고, `/opt/podman/bin/podman machine start`는 성공한다. 컨테이너 조작은 6.1.0으로도 된다.
- podman VM의 시계는 호스트가 CPU를 다 쓰는 동안 어긋났다가 맞춰진다. 그 사이 truncate가 미래 시각을 기록하면 이후에 쓴 레코드가 한동안 보이지 않아, 전체 실행에서 TTL·generation 테스트 150여 개가 한꺼번에 실패한다. 세 번 겪었고 매번 시계가 맞은 뒤 다시 돌리면 통과했다. 전체 실행이 대량으로 실패하면 `date -u`와 `podman exec aerospike date -u`부터 비교한다. 대량 실패의 다른 원인은 [재시작 테스트 뒤 되살아난 레코드](#테스트)다. 앞의 세 번 가운데 일부도 그것이었을 수 있다. 그때는 둘을 구분하지 않았다.
- 체크아웃한 `main` 작업 폴더에 이 문서가 untracked로 남아 있으면, 그 폴더에서 이 브랜치를 체크아웃할 때 충돌한다.

## 후속 작업

이번 릴리스에서 구현하지 않는다. #499가 의존성 업그레이드의 선행 조건이 아닌 별도 결정으로 분류한 항목이고, #315·#318은 2026-08-17에 `NOT_PLANNED`로 닫혀 있다.

- **SC 읽기 모드 4종**(`Session`·`Linearize`·`AllowReplica`·`AllowUnavailable`)과 **다중 레코드 트랜잭션**은 Enterprise Edition의 SC namespace가 있어야 검증할 수 있다. 저장소의 compose와 CI는 CE뿐이므로 EE 테스트 환경을 먼저 마련한다. 트랜잭션은 commit·abort·commit 결과 불확실 후 복구를 검증한다. [SC #315](https://github.com/aerospike-ce-ecosystem/aerospike-py/issues/315) · [트랜잭션 #466](https://github.com/aerospike-ce-ecosystem/aerospike-py/issues/466)
- **직렬화 가능한 재개 커서**는 `PartitionFilter` 직렬화를 쓰며, 이는 현재 켜지 않은 `serialization` cargo feature 뒤에 있다. 커서 복원에 쓰는 `partitions`·`PartitionStatus`는 upstream이 지원 API가 아니라고 숨겨 둔 필드다. 중단·재시작 후 누락과 중복을 검증한다. [커서 #318](https://github.com/aerospike-ce-ecosystem/aerospike-py/issues/318)
- **버퍼 설정 노출.** `use_buffer_pool`과 버퍼 크기 설정을 `ClientConfig`로 내보내면 [늘어난 메모리](#메모리는-늘었다)를 사용자가 조절할 수 있다.
- **배치의 레코드별 정책.** `batch_operate`의 `exists`·`gen`·`commit_level`과 `batch_remove`의 `exists`를 적용하거나, 받지 않는다고 거부한다.
- **upstream 보고.** [작업 중 발견한 것](#작업-중-발견한-것)의 Rust client 3.0 동작 열 가지를 보고할지 결정한다. callback API가 레코드마다 future를 박싱하는 것(`Box::pin(callback(res))`)과, 네트워크 청크 단위로 넘겨주는 callback이 없는 것도 함께 다룰 만하다. 바인딩은 그 상자에 16~24바이트짜리 값(넣기에 성공했는지, 아니면 기다리는 future의 포인터)만 들어가도록 했지만 레코드마다의 할당 자체는 남는다.
- **알려진 result code의 경고.** `FORBIDDEN`(22)처럼 이름이 있는 서버 코드에도 "Unmapped ResultCode" 경고가 남는다. 0.14.4도 같다. 부하 때 흔한 `KEY_BUSY`·`DEVICE_OVERLOAD`·`PARTITION_UNAVAILABLE`은 `08ea4ed`에서 경고를 없앴다.
- **sync `results()`는 Ctrl-C로 끊기지 않는다.** `e76a1d1` 뒤로 인터럽트가 사라지지는 않지만, scan이 끝나 호출이 반환할 때 올라온다. 기다리는 동안 주기적으로 신호를 확인해 query를 멈추게 할 수 있다.
- **태스크를 취소하지 않고 닫은 이벤트 루프.** 돌고 있던 `results()`가 아무도 기다리지 않는 채 끝까지 모으고 변환한다. 스트림 재검증에서 그 뒤의 `results()`가 0.07초 대신 2.3초 걸렸다. 변환 차례는 사라지지 않는다. `asyncio.run()`은 태스크를 취소하므로 해당하지 않는다.
- **재전송을 기다리는 단건 쓰기와 `close()`.** 위 "고치지 않고 문서에만 적은 것"의 `in_doubt=False`를 고치려면 바인딩이 단건 쓰기의 재시도를 직접 돌리거나, upstream이 재전송 시점의 라우팅 오류를 표시해야 한다.
- **라우팅하지 못한 행과 호출의 성패.** 클라이언트가 노드를 찾지 못해 스스로 코드(11, 20)를 찍은 행만 있는 배치는 예외 없이 행을 돌려준다. 서버가 답한 것이 아니므로 호출 실패로 볼지 정한다. 지금은 `test_batch_partial_result.py`가 반환하는 쪽을 고정하고 있다.
- **`AsyncClient.close()`와 열린 스트림.** 클라이언트를 닫아도 읽고 있던 스트림은 끝까지 읽는다. 닫을 때 스트림을 멈추게 할지 정한다.
- **`batch_write(retry=N)`이 올리는 예외.** 여러 시도에서 호출 전체가 실패하면 마지막 시도의 예외가 올라온다. 행마다의 상태는 `partial_result`에 있다.
- **query의 `max_retries: 0`.** 스트림 리뷰어의 실험에서 query에 `max_retries: 0`을 주면 쉬지 않고 무제한 재시도했다. 0.14.4도 같았다고 보고됐다. 직접 다시 재지는 않았다.
- **포화된 서버에서 작은 query의 꼬리 지연.** [성능에서 치른 비용](#성능에서-치른-비용)의 5번이다. 처리량의 한계가 서버에 있고 꼬리가 서버에 걸린 query 수를 따른다는 것까지는 쟀다. 0.14.4가 같은 서버 부하에서 꼬리가 짧은 이유는 가리지 못했다. 클라이언트와 CPU를 나누지 않는 서버에서 서버의 query 통계와 함께 다시 잰다.
- **큰 값의 `operate()`.** 원소 5,000개 list를 읽는 `operate()`의 호출당 CPU가 0.14.4보다 늘었다([성능](#성능-0144--브랜치) 참고). upstream이 연산 결과를 `results`에도 복사해 두기 때문으로 보이며, 확인하지 않았다.
- **map 범위 연산의 `end=None`.** `map_remove_by_key_range("m", "c", None)`처럼 끝을 `None`으로 준 map 범위 연산 3종에서 바인딩은 끝이 열린 범위로 처리하고 공식 클라이언트는 빈 결과를 낸다. 이 브랜치 이전부터 있던 차이이고, NumPy·ordered 재검증의 단일 연산 145개 비교에서 나왔다.
- **크기 0인 키 필드.** `("_key", "S0")`는 받아들여지고 모든 행이 빈 bytes 키로 기록된다. 거부할지 정한다. 0.14.4의 동작은 확인하지 않았다.
- **fuzz가 만들지 않는 입력.** `(1,)` 벡터에 들어가는 스칼라의 값 검사, 숫자 스칼라 필드에 bytes가 오는 경우, 행 stride와 dtype 파싱은 어느 fuzz 대상도 다루지 않는다.
- **tox의 free-threaded 패키징 환경.** 3.14t 환경이 GIL 빌드로 만든 wheel을 받지 않도록 한다.
- **재시작 테스트가 남기는 상태.** `-m destructive` 테스트가 끝난 뒤 namespace를 비우게 하거나, 테스트 정리를 재시작 뒤에도 유지되는 방식으로 바꾼다([테스트](#테스트)의 되살아난 레코드 참고).
- **넓은 레코드와 Linux에서의 변환 덩어리.** [로컬에서 확인하지 못한 것](#로컬에서-확인하지-못한-것)의 측정을 VM을 거치지 않는 환경에서 한다. 한 덩어리의 변환이 5 ms를 넘으면 레코드 수 대신 걸린 시간으로 덩어리를 끊는 방법이 있다.
- **큰 결과를 만들 때의 Python GC.** 10만 레코드 결과가 여럿 살아 있으면 전체 GC 한 번이 40~85 ms이고 그동안 이벤트 루프가 멈춘다. 리뷰 반영 전 빌드와 최종 빌드에서 같았다. 변환 중 GC를 미루는 것을 검토할 수 있다.
