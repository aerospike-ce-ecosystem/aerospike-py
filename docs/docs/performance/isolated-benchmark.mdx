The local `benchmark/` suite compares `aerospike-py.AsyncClient` with the synchronous `aerospike` C extension called via `asyncio.to_thread()`. A FastAPI endpoint reads records and returns a count or a scalar summary, so the clock includes HTTP, conversion and any inference the route performs. The [client comparison](./client-comparison) separately measures direct calls with `aerospike-py 0.14.4`, the updated client and `aerospike-sdk 1.0.0`.

## How to run the smoke workload {#how-to-run}

From the repository root, start the local CE 8.1.2.1_3 instance on port 18710 and seed `test/bench`. The harness uses uv, Podman and the oha load generator; `RUNTIME=docker` selects Docker for Compose.

```bash
cd benchmark
make sync PYTHON=3.11
make up
make seed
make bench-all CONCURRENCY=4 DURATION=3s BATCH_SIZE=30
make report
```

For each endpoint the runner starts one uvicorn worker per client in turn, waits for `/healthz` and drives HTTP requests for the specified duration. Each run writes `meta.json` and `oha.json` under `benchmark/results/`. `make report` prints comparison tables. [Harness at publication](https://github.com/aerospike-ce-ecosystem/aerospike-py/tree/7c6c0cec741e0a9ce65ab12e0375f83fad870c97/benchmark)

## Published smoke results {#scenarios}

The May 27, 2026 report recorded warm-cache runs on Python 3.11 with four concurrent HTTP clients, 30 keys per batch and three seconds per run. S4 used four groups of 30 keys. The report identifies the C library as 19.x and leaves the exact package builds unspecified. Per-run oha samples were not published with the table. Re-running the command uses the checkout and the packages resolved by uv. [Original published figures](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/7c6c0cec741e0a9ce65ab12e0375f83fad870c97/docs/docs/performance/isolated-benchmark.mdx)

| Endpoint | C requests/s | aerospike-py requests/s | C mean / p95 (ms) | aerospike-py mean / p95 (ms) |
|---|---:|---:|---:|---:|
| S1 · count hits | 2,383.2 | 2,466.8 | 1.68 / 2.14 | 1.62 / 2.39 |
| S2 · dict to inference | 1,986.0 | 2,206.6 | 2.01 / 2.48 | 1.81 / 2.56 |
| S3 · NumPy to inference | 1,854.0 | 2,466.2 | 2.16 / 2.75 | 1.62 / 2.36 |
| S4 · gather | 902.8 | 1,130.3 | 4.43 / 4.80 | 3.54 / 4.95 |
| S4 · single | 996.1 | 1,385.4 | 4.02 / 4.70 | 2.89 / 4.24 |
| S5 · consume eight fields | 2,421.4 | 2,722.0 | 1.65 / 2.09 | 1.47 / 2.16 |

### S1 · Count successful rows {#s1--pure-batch_read-round-trip}

Both clients fetch the records. aerospike-py calls the native `found_count()` on the returned handle. The C adapter iterates its Python batch rows and tests each result code. At this load aerospike-py had a lower mean and a higher p95. [Endpoint](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/7c6c0cec741e0a9ce65ab12e0375f83fad870c97/benchmark/src/app/routes/s1_read_only.py)

</TabItem>
<TabItem value="s2" label="S2 · dict to inference">

### S2 · Build a tensor from dicts {#s2--batch_read--dict--tensor--dlrm}

Both clients produce Python rows of 64 feature values, supply zeros for missing records, create a float32 tensor and run the same two-layer model. aerospike-py uses `to_dict()`; the C adapter reads the bins in each returned record. [Endpoint](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/7c6c0cec741e0a9ce65ab12e0375f83fad870c97/benchmark/src/app/routes/s2_dict_infer.py)

</TabItem>
<TabItem value="s3" label="S3 · NumPy to inference">

### S3 · Build a tensor from a NumPy matrix {#s3--batch_read--numpy-structured-array--torch--dlrm}

`to_numpy(dtype)` allocates and fills the structured result. The subsequent float32 view, reshape and `torch.from_numpy()` share the matrix storage. The C adapter fills its matrix from per-record dicts before calling the same model. With that whole path included, S3 handled 2,466 vs 1,854 requests/s. [Endpoint](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/7c6c0cec741e0a9ce65ab12e0375f83fad870c97/benchmark/src/app/routes/s3_numpy_infer.py)

</TabItem>
<TabItem value="s4" label="S4 · gather and single">

### S4 · Four batches or one mixed-key batch {#s4--asynciogathern-batch_reads-vs-single-batch_readmixed-keys}

`/s4/gather` submits four concurrent calls of 30 keys; `/s4/single` submits all 120 keys together. Each C call is dispatched through the thread pool. The single-call endpoint had lower mean and p95 latency for both clients in this run. [Endpoint](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/7c6c0cec741e0a9ce65ab12e0375f83fad870c97/benchmark/src/app/routes/s4_gather_vs_single.py)

</TabItem>
<TabItem value="s5" label="S5 · subset">

### S5 · Read eight feature fields {#s5--partial-materialisation-with-lazybatchrecords}

Both clients request all bins. aerospike-py fills a structured dtype containing eight of the 64 feature fields, and the C adapter reads those eight values from each returned dict. Both endpoints return their sum and the count of found records. [Endpoint](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/7c6c0cec741e0a9ce65ab12e0375f83fad870c97/benchmark/src/app/routes/s5_lazy_subset.py)

</TabItem>

## Measurement boundaries {#whats-deliberately-not-measured}

Each response contains a hit count or an aggregate. The table counts complete HTTP requests per second. The client-only batch benchmark counts individual records per second. For HTTP requests through a deployed inference service, see the [April serving benchmarks](./production-benchmark).

## Free-threaded Python coverage {#python-314t--runtime-swap-on-the-same-suite}

The published ASGI table covers ordinary Python 3.11. For ordinary and FT builds of the **same** CPython version, see the [3.14.2 client comparison](./client-comparison). For query iteration and event-loop wakeups, see the [async stream profile](./async-stream-profile).
