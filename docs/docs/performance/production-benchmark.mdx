These April 16–17, 2026 runs compared a development build of `aerospike-py` with the `aerospike` C extension. The accompanying profiling report identifies the builds as `aerospike-py v0.1.0` and `aerospike 19.2.0`. In this archive, `official` means the C extension. For the comparison with the previous `aerospike-py 0.14.4` release and the Rust-based `aerospike-sdk 1.0.0`, see [Client comparison](./client-comparison). [April profiling report](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/bottleneck-analysis.md)

## Where latency was measured {#where-the-gap-lives}

The three workloads measured a direct client call, an ASGI prediction endpoint, and an inference service under k6 load. Each reported its own concurrency, latency distribution and error count. They were separate runs.

## Environment A — direct client {#environment-a--pure-db-client}

### Conditions {#setup}

Nine sets, 50 or 200 keys per batch, 10 concurrent calls and 30 iterations per configuration. The harness called the C API synchronously as `official` or through `run_in_executor` as `official-async`. The `py-async` adapter used the native `aerospike-py` async API. The C adapters counted hits by walking result rows; `py-async` took the length of its result mapping. [Archived adapter source](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/src/benchmark/clients.py)

### Aggregate result {#aggregate-result-avg-over-9-sets--2-batch-sizes}

Each cell is an average across 18 set/size combinations. In particular, the p99 column averages 18 per-configuration percentiles. [Original report](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/20260416_134243/report.md) · [Per-configuration CSV](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/20260416_134243/summary.csv)

| Adapter | Average mean (ms) | Average p99 (ms) | Average batch calls/s |
|---|---:|---:|---:|
| C, synchronous | 107.56 | 195.34 | 138.2 |
| C, executor | 110.64 | 211.33 | 125.7 |
| aerospike-py, native async | 22.45 | 120.67 | 373.7 |

### Effect of hit rate {#per-set-speedup-distribution-aerospike-py-vs-official}

For the eight sets with hits, the ratio of C synchronous to aerospike-py mean latency ranged from 4.43–7.82× at 50 keys and 3.08–6.64× at 200 keys. All `set_8` reads missed. For that set, a 50-key batch took 13.92 ms with C and 15.20 ms with aerospike-py, while a 200-key batch took 19.95 and 16.27 ms respectively.

## Environment C — FastAPI and DLRM inference {#environment-c--uvicorn--dlrm-real-serving}

### Conditions {#setup-2}

Two Kubernetes replicas ran FastAPI, feature construction and PyTorch CPU inference. Each pod requested 4 CPUs and 4 GiB, with limits of 8 CPUs and 8 GiB. k6 ran 10 virtual users for 60 seconds each in the single-batch and gather scenarios. Each iteration called both endpoints sequentially in the shared-client configuration. The application fetched 9 sets × 200 keys per prediction. [k6 report and configuration](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/k6-runtime-client-comparison.md)

### Client-side latency {#k6-client-side-latency}

| CPython 3.11.14 · stage metrics off | aerospike-py | C extension |
|---|---:|---:|
| Single batch mean | 118 ms | 146 ms |
| Single batch p90 | 173 ms | 293 ms |
| Single batch p95 | 189 ms | 324 ms |
| Nine concurrent batches p95 | 234 ms | 266 ms |
| Merge-gather p95 | 202 ms | — |
| Stress ramp p95 | 592 ms | — |

### Server-side observations {#server-side-prometheus-same-run-single-mode}

For the single-batch scenario, the app's p95 prediction duration was 202 ms for aerospike-py and 274 ms for C. The p95 for the app's batch-read stage was 137 ms and 252 ms respectively. These Prometheus histograms used a 90-second window. A difference from k6's p95 does not give a per-request network time.

## Reading the three workloads {#pattern-across-environments}

For direct batch calls, the reported average mean latency was 107.56 ms for C and 22.45 ms for aerospike-py. For complete prediction requests, the single-batch p95 was 324 ms and 189 ms respectively. Application overhead, hit rate, concurrency and metric definition all changed across these comparisons.

## Historical CPython 3.11 and 3.14t runs {#python-314t-free-threaded--same-pipeline-gil-removed}

### Runtime and load configuration {#tldr}

The April study used CPython 3.11.14 and a 3.14.2t image. Stage metrics and endpoint availability also changed. The free-threaded run with both endpoints used a source-built C client. In the separate aerospike-py-only image, the C endpoint returned HTTP 503. [Runtime comparison](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/k6-runtime-client-comparison.md)

### Timing stages {#what-gets-faster-and-why}

An earlier 90-second curl load test used 20 workers and enabled stage metrics on both runtimes. Average `spawn_blocking_delay` was 234 ms on 3.11 and 0.12 ms on 3.14t. The 3.11 profiling run ended under memory pressure. For `event_loop_resume_delay`, 3.11 recorded 39.7 ms and the 3.14t comparison reported insufficient samples. These stage averages cannot be subtracted from the k6 request p95. [Stage timing report](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/python-3.14t-benchmark.md) · [Profiling load conditions](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/internal-stage-toggle-comparison.md)

### Single-batch p95 across runtime configurations {#same-workload-comparison-on-314t}

| Deployment | aerospike-py | C extension |
|---|---:|---:|
| 3.11, stage metrics off | 189 ms | 324 ms |
| 3.11, stage metrics on | 143 ms | 242 ms |

| Deployment | k6 iterations/s | HTTP requests/s |

The totals cover all scenarios, including requests to unavailable endpoints. They measure the load scripts' activity and include unsuccessful requests.

### Solo endpoint runs {#but-aerospike-py-still-wins-under-solo-load-on-314t}

The archived comparison reports single-batch request p95 of 97 ms for aerospike-py and 134 ms for C when each endpoint was tested separately. The gather p95 values were 107 ms and 253 ms. The two k6 scripts used different mixes of scenarios and requests per iteration. Their total throughput therefore represents different work. [Solo run details](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/k6-runtime-client-comparison.md)
