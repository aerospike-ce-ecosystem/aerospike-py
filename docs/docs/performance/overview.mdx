## Which benchmark matches your workload?

The [client comparison](./client-comparison.md) measures three versions side by side: aerospike-py built on Aerospike Rust client 3.0 at [commit `4aabf09`](https://github.com/aerospike-ce-ecosystem/aerospike-py/commit/4aabf09f7ca1911a5ba00a3d668ec799c19ed54c), the previous aerospike-py release **0.14.4**, and Aerospike’s **`aerospike-sdk` 1.0.0**. Each ran on CPython 3.14.2 and 3.14.2t against one local Aerospike CE 8.2.0.1 node.

### Batch throughput

Four synchronous threads each read or wrote 720 records with eight integer bins. Each column shows the percentage change in **rows per second** from that baseline to the new build. Dictionary writes include preparing each client's request from the input dictionaries.

The [client comparison](./client-comparison.md) includes absolute throughput, CPU per row, p99 per batch and single-caller results. For peak RSS at higher batch concurrency, see [memory under concurrent batch load](../guides/migration-0.15.md#memory-under-concurrent-batch-load).

### Async queries

On standard Python, consuming 12,000 rows with `async for` took **33.75 ms** with the new build and **336.53 ms** with the SDK. On free-threaded Python the times were **41.80 ms** and **196.64 ms**. The [stream profile](./async-stream-profile.md) shows what happened when the record delivery size and event-loop wake-up transport were changed independently. The SDK's `get_many()` submits independent point reads and has its own [window benchmark](./client-comparison.md#independent-point-operations).
