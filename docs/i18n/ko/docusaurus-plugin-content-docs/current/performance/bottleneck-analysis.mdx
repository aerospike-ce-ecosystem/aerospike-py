2026년 4월 서빙 실험에서는 HTTP 요청마다 9개 set에서 200키씩 읽었습니다. 앱은 병렬 호출 전체를 측정하고, 클라이언트 히스토그램은 각 `batch_read()`의 세부 구간을 측정했습니다. 9개 호출의 실행 시간이 겹치므로 각 호출의 구간 평균을 더해 HTTP 요청 한 건의 지연 시간을 구할 수 없습니다. 당시 보고서는 개발 빌드 `aerospike-py v0.1.0`과 C 확장 `aerospike 19.2.0`을 사용했다고 기록합니다. [4월 분석 보고서](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/bottleneck-analysis.md)

| 측정 구간 | 포함되는 작업 |
|---|---|
| HTTP 요청 | 키 구성, 모든 DB 호출, 결과 변환, 추론, 응답 |
| `batch_read()` 한 건 | 실행 슬롯 대기, 클라이언트 처리와 Aerospike 요청 |
| 결과 변환 | 소비자가 지연 핸들을 받은 뒤 `to_dict()` 또는 `to_numpy()`를 호출하는 작업 |

3.11과 3.14t를 비교한 curl 실험에서 평균 `spawn_blocking_delay`는 각각 234 ms와 0.12 ms였습니다. 3.11 실행은 메모리 부족을 겪었고, FT에서는 `event_loop_resume_delay` 표본이 부족했습니다. 당시 부하와 지표의 상세 조건은 [서빙 프로파일 기록](./production-benchmark#what-gets-faster-and-why)에 있습니다.

## 새로 측정할 때 {#재측정-시-다룰-내용}

1. 사용자가 기다리는 범위를 선택합니다. 예를 들어 NumPy 결과를 쓰는 엔드포인트에서는 `to_numpy()`와 배열 소비까지 측정합니다. 시간과 함께 성공한 행 수와 오류를 기록합니다.
2. `AEROSPIKE_PY_INTERNAL_METRICS=1` 또는 Python 컨텍스트 매니저로 `db_client_internal_stage_seconds`를 수집합니다. 같은 작업과 부하에서 `limiter_wait`, `io`, 결과 변환 구간을 비교합니다. [구간 정의와 활성화 방법](../integrations/observability/internal-stage-metrics.md)
3. 병렬 배치를 검증하려면 같은 총 키 개수로 `/s4/gather`와 `/s4/single`을 실행합니다. 배치 호출 수와 함께 HTTP p95와 오류 수를 기록합니다. [로컬 ASGI 시나리오](./isolated-benchmark)

현재 CPython 3.14.2의 배치 측정값은 [클라이언트 비교](./client-comparison)에 있습니다. 쿼리 순회에서 한 행씩 또는 여러 행씩 결과를 넘기는 비용은 [비동기 스트림 프로파일](./async-stream-profile)에 정리했습니다.
