2026년 4월 16~17일 실험은 개발 중인 `aerospike-py`와 `aerospike` C 확장을 비교했습니다. 당시 프로파일링 보고서가 기록한 버전은 `aerospike-py v0.1.0`과 `aerospike 19.2.0`입니다. 이 기록의 `official`은 C 확장을 가리킵니다. 직전 릴리스 `aerospike-py 0.14.4` 및 Rust 기반 `aerospike-sdk 1.0.0`을 기준으로 한 수치는 [클라이언트 비교](./client-comparison)에 있습니다. [당시 프로파일링 보고서](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/bottleneck-analysis.md)

## 지연 시간을 측정한 범위 {#격차가-어디-있는가}

직접 호출한 배치 읽기, ASGI 예측 엔드포인트, k6로 부하를 준 추론 서비스에서 각각 측정했습니다. 세 실험은 동시 호출 수, 요청 구성, 오류율이 다릅니다.

## 환경 A — 클라이언트 직접 호출 {#environment-a--pure-db-client}

### 측정 조건 {#setup}

9개 set, 배치당 50개 또는 200개 키, 동시 호출 10개로 각 구성에서 30회 반복했습니다. `official`은 C API를 동기 호출하고, `official-async`는 같은 동기 API를 `run_in_executor`로 호출했습니다. `py-async`는 `aerospike-py`의 네이티브 비동기 API를 사용했습니다. C 어댑터는 결과 행을 순회해 적중 건수를 셌고, `py-async`는 반환된 매핑의 길이를 읽었습니다. [당시 어댑터 코드](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/src/benchmark/clients.py)

### 전체 결과 {#aggregate-결과-9-sets--2-batch-sizes-평균}

각 값은 18가지 set·배치 크기 조합의 평균입니다. p99 열도 각 조합의 p99를 구한 뒤 평균을 냈습니다. [당시 보고서](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/20260416_134243/report.md) · [조합별 CSV](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/20260416_134243/summary.csv)

| 호출 경로 | 평균 지연의 평균 (ms) | p99의 평균 (ms) | 평균 배치 호출/초 |
|---|---:|---:|---:|
| C 동기 | 107.56 | 195.34 | 138.2 |
| C + executor | 110.64 | 211.33 | 125.7 |
| aerospike-py 네이티브 비동기 | 22.45 | 120.67 | 373.7 |

### 적중률에 따른 차이 {#per-set-speedup-분포-aerospike-py-vs-official}

적중한 레코드가 있는 8개 set에서 C 동기 호출 시간 ÷ aerospike-py 호출 시간은 50키일 때 4.43~7.82배, 200키일 때 3.08~6.64배였습니다. `set_8`에서는 모든 키가 미적중했습니다. 이 set의 평균 시간은 50키에서 C 13.92 ms, aerospike-py 15.20 ms였고, 200키에서 각각 19.95 ms와 16.27 ms였습니다.

## 환경 C — FastAPI와 DLRM 추론 {#environment-c--uvicorn--dlrm-실-서빙}

### 측정 조건 {#setup-2}

Kubernetes 복제본 2개에서 FastAPI, 특성 생성, PyTorch CPU 추론을 실행했습니다. pod당 요청 자원은 CPU 4개와 4 GiB, 제한은 CPU 8개와 8 GiB였습니다. k6는 가상 사용자 10명으로 단일 배치 및 gather 시나리오를 각각 60초 실행했습니다. 두 엔드포인트를 함께 배포한 구성에서는 매 iteration에 양쪽을 차례로 호출했습니다. 예측 요청 하나가 9개 set에서 각각 200키를 읽었습니다. [k6 결과와 구성](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/k6-runtime-client-comparison.md)

### k6에서 본 지연 시간 {#k6-client-side-latency}

| CPython 3.11.14 · 구간 지표 비활성 | aerospike-py | C 확장 |
|---|---:|---:|
| 단일 배치 평균 | 118 ms | 146 ms |
| 단일 배치 p90 | 173 ms | 293 ms |
| 단일 배치 p95 | 189 ms | 324 ms |
| 동시 배치 9개 p95 | 234 ms | 266 ms |
| Merge-gather p95 | 202 ms | — |
| 스트레스 부하 p95 | 592 ms | — |

### 서버에서 본 지연 시간 {#server-side-prometheus-동일-run-single-mode}

단일 배치 시나리오에서 앱이 측정한 예측 p95는 aerospike-py 202 ms, C 274 ms였고, 앱의 배치 읽기 구간 p95는 각각 137 ms와 252 ms였습니다. Prometheus 히스토그램은 90초 구간을 사용했습니다. 이 p95와 k6 p95의 차이만으로 요청당 네트워크 시간을 구할 수 없습니다.

## 세 환경의 결과 읽기 {#환경별-패턴}

직접 배치 읽기의 조합별 평균 지연은 C 107.56 ms, aerospike-py 22.45 ms였습니다. 추론을 포함한 단일 배치 예측 요청의 p95는 각각 324 ms와 189 ms였습니다. 두 실험 사이에는 앱에서 처리하는 작업, 적중률, 동시 호출 수, 지표의 정의가 달라졌습니다.

## CPython 3.11과 3.14t의 과거 측정 {#python-314t-free-threaded--same-pipeline-gil-removed}

### 런타임과 부하 구성 {#tldr}

4월 실험은 CPython 3.11.14와 3.14.2t 이미지를 사용했습니다. 구간 지표 설정과 호출 가능한 엔드포인트도 구성마다 달랐습니다. FT에서 두 엔드포인트를 함께 실행한 이미지는 C 클라이언트를 소스에서 빌드했습니다. aerospike-py만 설치한 별도 이미지에서는 C 엔드포인트가 HTTP 503을 반환했습니다. [런타임 비교 보고서](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/k6-runtime-client-comparison.md)

### 구간별 시간 {#what-gets-faster-and-why}

별도의 curl 실험에서는 worker 20개로 90초 동안 부하를 주고 두 런타임 모두 구간 지표를 활성화했습니다. 평균 `spawn_blocking_delay`는 3.11에서 234 ms, 3.14t에서 0.12 ms였습니다. 3.11 프로파일링 실행은 메모리 부족으로 종료됐습니다. `event_loop_resume_delay`는 3.11에서 39.7 ms였고, 3.14t는 표본이 부족했습니다. 이 구간 평균을 k6 요청 p95에서 빼는 방식으로 각 구간의 기여도를 구할 수 없습니다. [구간별 결과](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/python-3.14t-benchmark.md) · [프로파일링 당시 부하 조건](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/internal-stage-toggle-comparison.md)

### 구성별 단일 배치 p95 {#314t-의-same-workload-비교}

| 배포 구성 | aerospike-py | C 확장 |
|---|---:|---:|
| 3.11, 구간 지표 비활성 | 189 ms | 324 ms |
| 3.11, 구간 지표 활성 | 143 ms | 242 ms |
| 3.14t, 지표 활성, aerospike-py 엔드포인트 제공 | 97 ms | — |
| 3.14t, 지표 활성, 두 엔드포인트 제공 | 126 ms | 128 ms |

### k6 실험 전체의 처리량 {#throughput-tps}

| 배포 구성 | k6 iteration/초 | HTTP 요청/초 |
|---|---:|---:|
| 3.11, 지표 비활성 | 41.6 | 50.8 |
| 3.11, 지표 활성 | 44.1 | 52.9 |
| 3.14t, aerospike-py 엔드포인트 제공 | 61.2 | 80.0 |
| 3.14t, 두 엔드포인트 제공 | 47.3 | 59.8 |

실패하거나 해당 이미지에서 제공하지 않는 엔드포인트로 보낸 요청까지 모든 시나리오의 부하 생성 횟수에 포함됩니다.

### 단일 엔드포인트 부하 {#그래도-solo-load-에선-aerospike-py-가-여전히-우위-314t}

각 엔드포인트에 별도로 부하를 준 실험에서 단일 배치 요청의 p95는 aerospike-py 97 ms, C 134 ms였습니다. gather p95는 각각 107 ms와 253 ms였습니다. 두 k6 스크립트는 시나리오 구성과 iteration당 요청 수가 달라 전체 처리량을 계산할 때 작업량도 달라집니다. [단독 부하 실험 상세](https://github.com/aerospike-ce-ecosystem/aerospike-py/blob/524cadf9d5864ed8aeeabdfca88861eca4113cfe/benchmark/results/k6-runtime-client-comparison.md)

### 비교 기준 선택 {#migration-notes}

현재 클라이언트를 고를 때는 [클라이언트 직접 비교](./client-comparison)를, 현재 비동기 iterator의 GIL 상태와 완료 알림 방식에 따른 차이는 [비동기 스트림 프로파일](./async-stream-profile)을 참고하세요. uvicorn HTTP 시나리오를 로컬에서 실행하는 방법은 [ASGI 스모크 벤치마크](./isolated-benchmark)에 있습니다.
